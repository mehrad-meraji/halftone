# Accessibility

Status as of 2026-10-19: 0 axe violations across 169 stories added for the 20 newer components (run after two fixes: table scroll box moved onto the table host, disabled calendar no longer dims its title) on top of the first pass below. First pass, 2026-10-12: 0 axe violations across 115 stories in light and dark, WCAG 2.2 A and AA plus axe best practices. Behaviour checked by hand: keyboard (tabs, dialog, prompt, switch, select), form participation, focus return, `role` and `aria-*` wiring.

## How it is checked

| Check | Tool | Covers |
|---|---|---|
| Automated rules, incl. text contrast | `scripts/a11y-runner.js` (axe-core 4.10, run in Storybook) | Every story, both themes |
| Contrast axe cannot see | `node scripts/contrast.mjs` | Button faces (pseudo-element fills), field borders and focus rings (non-text, 3:1), switch icon |
| Behaviour | Manual, in Storybook | Keyboard, focus, forms, ARIA state |

Re-run both after any change to `src/tokens/tokens.css`. Keep the table in `scripts/contrast.mjs` in step with the tokens.

## Findings from the first pass and what changed

| Finding | Where | Fix |
|---|---|---|
| `--ht-text-subtle` under 4.5:1 on tinted fills (4.2 to 4.3) | Light and dark: input affixes, speech-bubble author | Light `0.54` to `0.50`, dark `0.64` to `0.68` |
| Prompt placeholder hint 2.2 to 3.3:1 (token at 70% opacity) | `ht-prompt` | No opacity; placeholder uses `--ht-text-muted`, hint `--ht-text-subtle` |
| Warning, success and tag text 2.0 to 2.7:1 in dark mode | `ht-tag`, `ht-banner` icons | Tone colours were mixed toward black; now mixed toward `--ht-text` (theme-aware), in `oklab` so the hue does not swing |
| White text on the dark-mode danger fill 3.4:1 | `ht-toast`, `ht-button` danger | `--ht-danger-ink` is dark in the dark theme (5.4:1) |
| Switch with `aria-label` on the host had no accessible name; `aria-label` on a generic host is prohibited | `ht-switch` | `label` property, and a host `aria-label` is moved to the native input |
| Same trap for fields with no visible label | `ht-input`, `ht-select` | Host `aria-label` is forwarded to the native control |
| Field outline 1.3:1 against the surface (WCAG 1.4.11 needs 3:1) | `ht-input`, `ht-select`, `ht-prompt` | New `--ht-border-input` token (3.3 to 3.4:1). Sentry's own fields use the paler border and would fail this |
| Disabled prompt placeholder flagged | `ht-prompt` | Overlay marked `aria-disabled`. Disabled controls are exempt from WCAG contrast |

## Known limits

- Axe does not check keyboard operability or screen reader announcements. The behaviours above were exercised by script and by hand, not with a screen reader.
- `ht-tooltip` adds `aria-description` to its trigger. Support is good in Chromium and Safari, patchier elsewhere, so never put required information in a tooltip.
- `ht-select` uses the browser's own menu, so that popup follows the OS theme rather than Halftone's.
- `ht-dialog` relies on the native `<dialog>`: focus is trapped and returned by the browser, but background scroll is not locked.
- `ht-tree` follows the WAI-ARIA tree pattern (single tab stop, arrows, type-ahead, `aria-level`, `aria-setsize`, `aria-posinset`, `aria-expanded`). Each item's name is set explicitly from its own label. Screen readers differ in how they announce deep trees, and this has not been tried with VoiceOver or NVDA.
- Toasts that dismiss on a timer are a risk for people who read slowly. Use `duration: 0` for anything the user must act on.
- `ht-radio` and `ht-checkbox` use native inputs inside each shadow root. Radios in separate shadow roots are not grouped by the browser, so `ht-radio-group` implements the radio pattern itself (one tab stop, arrows move and select, wrap-around). It follows WAI-ARIA but has not been tried with a screen reader.
