# Accessibility

Status as of 2026-10-19 (after the violet palette: 0 axe violations on all 278 stories in light and dark, and every pair in `scripts/contrast.mjs` passes): 0 axe violations across 169 stories added for the 20 newer components (run after two fixes: table scroll box moved onto the table host, disabled calendar no longer dims its title) on top of the first pass below. First pass, 2026-10-12: 0 axe violations across 115 stories in light and dark, WCAG 2.2 A and AA plus axe best practices. Behaviour checked by hand: keyboard (tabs, dialog, prompt, switch, select), form participation, focus return, `role` and `aria-*` wiring.

## How it is checked

| Check | Tool | Covers |
|---|---|---|
| Automated rules, incl. text contrast | `scripts/a11y-runner.js` (axe-core 4.10, run in Storybook) | Every story, both themes |
| Contrast axe cannot see | `node scripts/contrast.mjs` | Button faces (pseudo-element fills), field borders and focus rings (non-text, 3:1), switch icon |
| Behaviour | Manual, in Storybook | Keyboard, focus, forms, ARIA state |

Re-run both after any change to `src/tokens/tokens.css`. Keep the table in `scripts/contrast.mjs` in step with the tokens.

| Switch with `aria-label` on the host had no accessible name; `aria-label` on a generic host is prohibited | `ht-switch` | `label` property, and a host `aria-label` is moved to the native input |

| Disabled prompt placeholder flagged | `ht-prompt` | Overlay marked `aria-disabled`. Disabled controls are exempt from WCAG contrast |

## Known limits

- Axe does not check keyboard operability or screen reader announcements. The behaviours above were exercised by script and by hand, not with a screen reader.
- `ht-tooltip` adds `aria-description` to its trigger. Support is good in Chromium and Safari, patchier elsewhere, so never put required information in a tooltip.
- `ht-select` is a custom list (a popover in the top layer). Focus moves onto the options, as in Radix Select. It has been checked with axe, by script and by hand, but not with a screen reader.
- `ht-dialog` relies on the native `<dialog>`: focus is trapped and returned by the browser, but background scroll is not locked.
- `ht-tree` follows the WAI-ARIA tree pattern (single tab stop, arrows, type-ahead, `aria-level`, `aria-setsize`, `aria-posinset`, `aria-expanded`). Each item's name is set explicitly from its own label. Screen readers differ in how they announce deep trees, and this has not been tried with VoiceOver or NVDA.
- `ht-avatar` with `art` draws a picture from a seed. It is decoration (`aria-hidden`) until the avatar has a `name`, which is its only accessible label. Its fixed palette is measured by rows in `scripts/contrast.mjs`, not by axe (axe skips graphics): figure on background 3.3:1 or more, eyes and mouth on the face 5.0:1 or more. Forced-colours mode keeps the picture's colours and adds a `CanvasText` edge; it was not tried in a real forced-colours browser.
- Toasts that dismiss on a timer are a risk for people who read slowly. Use `duration: 0` for anything the user must act on. Older toasts in the collapsed stack are hidden from sight (their content is at 0 opacity) but stay in the accessibility tree, and each toast is its own live region, so a screen reader announces every one as it arrives. Toasts past `visible-toasts` are `inert`, so Tab never lands on a button nobody can see.
- `ht-alert` with `tone="danger"` is `role="alert"`, so it is announced when it appears. Other tones are `role="status"`. Links nested inside a slotted paragraph keep the page's own link colour: shadow styles reach only direct children of a slot.
- `ht-radio` and `ht-checkbox` use native inputs inside each shadow root. Radios in separate shadow roots are not grouped by the browser, so `ht-radio-group` implements the radio pattern itself (one tab stop, arrows move and select, wrap-around). It follows WAI-ARIA but has not been tried with a screen reader.
